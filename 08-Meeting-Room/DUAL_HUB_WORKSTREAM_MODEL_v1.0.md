# HBI — DUAL-HUB WORKSTREAM MODEL v1.0
Date: 2026-08-22
Authorized By: Engineer Maqsoudi (Product Owner)

## Core Principle
From this point forward, each Hub owns a stable Workstream. Members of a Hub will execute consecutive Tasks within their domain without micro-management handshakes.

## Hub A — Technical / Engineering (Manager: Qwen1)
- **Qwen1:** Gate Approval, Technical Governance, Technical Verdict.
- **DeepSeek1:** Backend, Tests, Execution Environment, CI, Performance Implementation.
- **Grok1:** Performance Testing, Technical Stress Testing, Technical Red-Team.
- **Domain:** Production Code, Backend, Test Implementation, Technical Gate Approval.

## Hub B — Reality / Documentation / Governance (Manager: ChatGPT)
- **ChatGPT:** WORK-REGISTRY, Reality Check, Cross-Hub coordination, Conflict adjudication.
- **Qwen2:** Handover, Documentation, Archive, Trace records.
- **DeepSeek2:** Execution Observation, CI Observer, Test Evidence collection.
- **Grok2:** Governance Red Team, Independent Reality Check, Conflict detection.
- **Domain:** Documentation, Handover, WORK-REGISTRY, Reality Check, Governance Audit.

## Absolute Boundaries (NO CROSS-INTERFERENCE)
- Hub A MUST NOT edit Documentation, Handover, or WORK-REGISTRY.
- Hub B MUST NOT edit Production Code, Backend, or Test Implementation.
- Final Business/Product Decisions rest SOLELY with the PO.

## The "No Task Ping-Pong" Rule
Every Task must define upfront:
[TASK | OWNER | WORKSTREAM | INPUT | EXPECTED OUTPUT | EVIDENCE REQUIRED | REVIEWER | FINAL AUTHORITY]
The Owner is responsible for the entire chain within their Workstream until Gate Review.

## File Ownership
Every Artifact has a single Owner. Concurrent independent editing of the same Artifact by different Hubs is FORBIDDEN to prevent Merge Conflicts.

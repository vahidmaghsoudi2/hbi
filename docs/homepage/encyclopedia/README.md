# دانشنامه

**جایگاه در HBI:** دانشنامه مرجع اصلی، زنده و قابل ویرایش انسانی برای گردآوری، سازمان‌دهی، بازبینی، نگهداری و دسترسی به دانش تأییدشده است. این جایگاه آن را به Pillar چهارم یا پایگاه عملیاتی موازی تبدیل نمی‌کند.

**مسیر جاری دانش محصول:**

`Approved Encyclopedia → Evidence / Source Traceability → ProductKnowledge → Consultation`

- دانشنامه مرجع انسانی اصلی برای محتوای تأییدشدهٔ محصول است؛ اطلاعات محصول در مسیر پژوهش و بازبینی از همین‌جا سازمان‌دهی و تکمیل می‌شود.
- سند سازنده، متن بسته‌بندی، سند فنی و منبع علمی اولیه حذف یا با خلاصهٔ دانشنامه جایگزین نمی‌شوند؛ منبع و محدودیت هر گزارهٔ مهم باید قابل ردیابی بماند.
- Evidence و Source Traceability نقش پشتیبان برای منشأ و بررسی گزاره‌ها دارند؛ بانک موازی، Pillar جداگانه یا Gate تأیید تکراری نیستند.
- ProductKnowledge بانک عملیاتی واحدی است که اطلاعات پذیرفته‌شده را برای استفادهٔ runtime در اختیار HBI قرار می‌دهد.
- تأیید PO پایان پذیرش محتوای محصول است؛ پس از آن تأیید محتوایی یا QA تکراری ایجاد نمی‌شود. کنترل‌های مستقل ایمنی و چرخهٔ عمر در جای خود باقی می‌مانند.

## مرزهای اختیار و منابع

- تصمیم معماری سه‌بخشی و مسیر ProductKnowledge: [HBI-PO-DEC-THREE-PART-001](../../03_decision_log/HBI-PO-DEC-THREE-PART-001.md).
- تصمیم جایگاه دانشنامه به‌عنوان مرجع اصلی دانش تأییدشده: [HBI-PO-DEC-ENCYCLOPEDIA-PRIMARY-KB-001 در Issue #406](https://github.com/vahidmaghsoudi2/hbi/issues/406#issuecomment-6989651765).
- تصمیم‌ها، مجوزها و Gateهای حوزهٔ ویژگی‌های محصول: [Issue #406](https://github.com/vahidmaghsoudi2/hbi/issues/406).
- فهرست عملیاتی ProductKnowledge: [KB_INDEX](../../05_knowledge_base/KB_INDEX.md).
- منابع و قابلیت ردیابی شواهد: [EVIDENCE_INDEX](../../07_evidence/EVIDENCE_INDEX.md).
- سندهای سازنده و بسته‌بندی، منابع اولیه‌اند و باید در کنار محتوای دانشنامه قابل بازیابی بمانند.

**منوی واقعی برنامه:** `frontend/src/pages/NewHomePage.tsx` (کارت دانشنامه). تغییر مستندات به‌تنهایی UI تولید را تغییر نمی‌دهد.

## قواعد ثبت و بازبینی

1. محتوای تأییدشدهٔ محصول در دانشنامه به‌عنوان مرجع انسانی اصلی نگهداری می‌شود.
2. برای هر گزارهٔ مهم، منبع اولیه، بازار/نسخه و محدودیت مرتبط را حفظ کنید.
3. ادعای سازنده را با برچسب `MANUFACTURER_CLAIM` نگه دارید؛ آن را بدون پشتوانه به واقعیت مستقل تبدیل نکنید.
4. `UNKNOWN`، `CONFLICT`، `PARTIAL` و اطلاعات بررسی‌نشده را آشکار نگه دارید؛ نبود داده به معنی بی‌خطری یا نبود ویژگی نیست.
5. پژوهش یا خلاصهٔ دانشنامه جایگزین متن کامل منبع اولیه نمی‌شود.
6. پس از تأیید PO، محتوای پذیرفته‌شده از مسیر ردیابی منبع به ProductKnowledge عملیاتی منتقل/منعکس می‌شود؛ Gate محتوایی دوم ایجاد نکنید.
7. دانشنامه و ProductKnowledge جایگزین Product Master، موجودی، وضعیت چرخهٔ عمر یا قواعد عملیاتی محصول نیستند.

## ساختار داخلی دانش پوست

مسیر ناوبری مصوب و جاری در هوم‌پیج:

دانشنامه → دانش پوست → (ویژگی محصولات پوستی | مشکلات پوستی)

- **ویژگی محصولات پوستی:** مرجع دانش انسانی و پرونده‌های محصول در [PRODUCTS.md](./skin/PRODUCTS.md). وضعیت تأیید هر بخش باید روشن باشد؛ پیش‌نویس پژوهش به‌جای دانش پذیرفته‌شده نمایش داده نشود.
- **مشکلات پوستی:** پیوند به [Workspace Index بانک مرجع P01–P61](../../product-intake-knowledge-registry/SKIN_PROBLEM_BANK_WORKSPACE_INDEX.md).
- این دو مقصد از نظر دامنه و مرجع تخصصی مستقل‌اند؛ هیچ‌یک داده‌های دیگری را کپی نمی‌کند. ارتباط مستند محصول/مشکل از ProductProblemLink موجود پیروی می‌کند.
- این ساختار ناوبری به معنی افزودن Pillar یا بانک موازی نیست.

## قواعد نگهداری

1. تصمیم‌های جاری معماری و دانشنامه در اسناد PO و Issue #406 مرجع‌اند؛ اسناد تاریخی متعارض باید با ارجاع اصلاح شوند، نه اینکه تاریخچهٔ ممیزی حذف شود.
2. زیرمنوهای اصلی دانشنامه حذف نمی‌شوند؛ محتوای داخل آن‌ها با حفظ سابقه و وضعیت پذیرش ویرایش می‌شود.
3. ثبت دانشنامه به‌تنهایی Product Master یا ProductKnowledge عملیاتی را تغییر نمی‌دهد.
4. هیچ ادعای پزشکی، ویژگی محصول یا نتیجهٔ اثربخشی بدون منبع و برچسب درست به‌عنوان دانش پذیرفته‌شده ثبت نشود.
5. Issue یا PR موازی برای همین ساختار نسازید مگر مالک محصول بخواهد.

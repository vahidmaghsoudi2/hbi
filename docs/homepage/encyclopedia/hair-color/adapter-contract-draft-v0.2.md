# HBI Consultation Engine Adapter Contract — Draft 0.2

- Status: design draft; D-01–D-08 approved by PO for documentation/design semantics on 2026-11-12; not approved for implementation
- Scope: conceptual request/response boundary between the HBI Consultation Orchestrator and a consultation engine
- Repository branch: `docs/hair-color-independent-consultation-20261112`
- Related PR: #535 (must remain Draft and unmerged)
- Catalogue: the 88-color catalogue is out of scope and must not be modified
- Data policy: synthetic fixtures only in GitHub/CI; real customer data remains in the PO's offline local environment

## 1. Purpose and non-goals

The Adapter is a stateless contract boundary. It validates a request assembled by trusted HBI services, invokes the selected engine, validates the engine response, and returns a normalized result or a fail-closed error.

The Adapter is not the owner of:
- case records, case versions, or target versions;
- client questions, rejection, acceptance, or stop events;
- execution consent or authorization to perform a service;
- workflow transitions or recording performed steps;
- scientific evidence approval or product identity authority.

The Adapter does not execute chemical services, create formulas, infer product chemistry from similar shade numbers, or turn evidence availability into permission to issue chemical instructions.

This document defines no runtime API, database, JSON Schema, engine stub, production behavior, pilot, or release. Those require separate explicit approval.

## 2. System boundary and trust model

Expected call path:

1. Client/operator interaction is interpreted by the Consultation Orchestrator.
2. The Orchestrator obtains the authoritative case snapshot, case version, target version, prior suggestion ledger, customer decision events, and workflow state from trusted stores.
3. The Orchestrator resolves applicable policy and evidence references.
4. The Adapter validates the request envelope and passes a bounded context to the engine.
5. The engine returns a candidate consultation result.
6. The Adapter validates structure, references, version alignment, state compatibility, and safety invariants.
7. The Orchestrator applies case-history rules and decides what may be shown to the client.
8. Only the Workflow Engine may mutate workflow state. Case Store/Audit Log remain authoritative for case and event history.

The engine must not be trusted to authoritatively assert case history, customer decisions, workflow state, or execution consent. Such information is read-only context from trusted stores. A model-generated field cannot override the authoritative record.

## 3. Independent state layers

These layers must never be collapsed into one `primary_status`.

### 3.1 Engine/motor state — four conceptual states

The following four meanings and proposed identifiers were approved by the PO for design-level use on 2026-11-12 (D-01). This does not authorize runtime enum/schema implementation:

| Proposed identifier | Meaning |
|---|---|
| `SUGGESTION_REVIEWABLE` | A reasoned candidate suggestion is available for review |
| `CONDITIONAL_SUGGESTION` | A suggestion is valid only if explicitly stated conditions are met |
| `NEEDS_MORE_INFORMATION` | Required information or test is missing |
| `STOP_OR_REFER_WITH_REASON` | The current run must stop or refer, with a reason |

A conditional suggestion is an engine state, not a sixth consultation response state.

### 3.2 Consultation response state — five approved meanings

The response state is one of the following five meanings, matching the README. The meanings and proposed identifiers were approved by the PO for design-level use on 2026-11-12 (D-02); this does not authorize runtime enum/schema implementation:

| Proposed identifier | Meaning |
|---|---|
| `SYSTEM_REASONED_SUGGESTION` | System can provide a reasoned, traceable suggestion |
| `NEEDS_INFORMATION_OR_TEST` | Missing information or test prevents a defensible suggestion |
| `NEEDS_IN_PERSON_OR_SPECIALIST_REVIEW` | Remote assessment is insufficient |
| `SAFETY_STOP_NO_EXECUTION_SUGGESTION` | Safety concern blocks an execution suggestion |
| `OUT_OF_V1_SCOPE` | Request is outside the approved first-version scope |

These identifiers are approved design-level names, not yet implemented runtime enums. “Approved for execution” is a workflow decision, not a consultation response state.

### 3.3 Workflow state — ten states, owned elsewhere

The workflow remains the ten-state model already recorded in the project. The Adapter may return information useful to the Workflow Engine, but it must not mutate or claim ownership of any workflow state.

## 4. Request contract (conceptual)

A request contains:

- `contract_version`: contract version requested;
- `request_id`: unique request identifier generated by the Orchestrator;
- `operation`: one of `EVALUATE_CASE`, `ANSWER_QUESTION`, or `REEVALUATE`;
- `case_ref`, `case_version`, `target_version`: authoritative identifiers from Case Store;
- `case_context`: the minimum relevant, provenance-bearing case snapshot;
- `question`: present for a client question; not itself a decision event;
- `evidence_context`: references to evidence records, not model-invented evidence;
- `policy_context`: applicable versioned policy constraints.

`RESUME_CHECK` is not an operation. A client request to restart after stopping must be represented as a new evaluation request built from a fresh case snapshot, current goal, current safety information, current rules, and current evidence. It must never resume the old path automatically.

### 4.1 Data knowledge state and provenance

For every safety-relevant or decision-relevant datum, preserve the distinction between:
- `KNOWN`: a value is explicitly recorded;
- `UNKNOWN`: the real-world value is unknown;
- `NOT_ASKED`: the question has not been asked;
- `MISSING`: a required field was not supplied in this request/snapshot;
- `CONFLICT`: authoritative records disagree;
- `NOT_APPLICABLE`: the field does not apply.

These states are not interchangeable. In particular, `false` must not stand in for unknown or not asked.

Each datum should carry its source class, record reference, and recorded time where available. Source classes may include `CLIENT_REPORTED`, `OPERATOR_RECORDED`, `SPECIALIST_OBSERVED`, `PRODUCT_DOCUMENT`, `INSTRUMENT_MEASURED`, and `SYSTEM_DERIVED`. A derived value must never be represented as a direct client report or physical observation.

### 4.2 Exact product identity

Where product-specific evidence is required, its identity must resolve to the exact brand, line/series, product/shade, market, and document/version scope. Similar brand names, shade numbers, or codes do not establish chemical equivalence.

## 5. Response contract (conceptual)

A successful engine response contains:
- request and case identifiers;
- evaluated case and target versions;
- one engine state;
- one of the five consultation response states;
- reason codes, separate from state values;
- a client-readable summary;
- zero or more candidate options;
- conditions, missing information, evidence references, limitations, and next step.

The Adapter's transport/validation result is separate from the engine's consultation result. A malformed engine response is an Adapter/engine failure, not a consultation status.

### 5.1 Reason codes

At minimum, distinguish:
- `DATA_GAP`: relevant case data is insufficient;
- `KNOWLEDGE_GAP`: applicable, reliable knowledge/evidence is unavailable;
- `ENGINE_FAIL`: engine, retrieval, or processing failed;
- `CONFLICTING_DATA`: relevant recorded sources conflict;
- `SAFETY_CONCERN`: a safety constraint blocks an execution suggestion;
- `OUT_OF_SCOPE`: the request is outside the approved scope;
- `STALE_CASE_VERSION`: the evaluated snapshot is no longer current.

These are diagnostic/reason codes, not additional consultation states. `DATA_GAP`, `KNOWLEDGE_GAP`, and `ENGINE_FAIL` must remain distinguishable.

### 5.2 Option invariants

- A safety-stop response must contain an empty `options` array.
- An engine failure must not publish any candidate option from the failed run.
- A candidate without applicable, traceable evidence must not be returned as an executable suggestion.
- Only valid options that pass all hard constraints may be ranked.
- If three valid options exist, no more than three are returned; if only one is valid, return exactly one; never invent options to fill a quota.
- Ranking must not depend on input array order.
- Each candidate option is bound to the evaluated target/case version. The engine may return candidate content and a request-local candidate key, but it cannot mint or assert an authoritative suggestion_ref, suggestion history, or active/rejected status. The Orchestrator/Case Store assigns the persistent suggestion identifier and records the candidate only after validation. For an explanatory question such as S11, any referenced existing suggestion must be resolved from the authoritative ledger; the engine cannot create or reactivate it.
- Rejected suggestions are filtered using the authoritative suggestion ledger, not by trusting the engine to remember rejections.
- A question does not change acceptance or execution consent.
- Acceptance of a suggestion is not execution consent.
- The engine cannot create or modify acceptance, consent, stop events, performed steps, or workflow state.

### 5.3 Chemical instruction boundary

The field `chemical_instruction_allowed` is intentionally absent. The V1 contract does not grant the engine authority to emit formulas, oxidant percentages, processing times, or other chemical execution instructions. Evidence alone does not grant such authority. Any future change requires explicit PO approval and separate specialist/evidence validation.

## 6. Fail-closed validation rules

The Adapter/Orchestrator must reject or suppress the current run when:
- contract version is unsupported;
- request or case identifiers do not match;
- case or target version is stale;
- required data is missing or contradictory and materially affects the decision;
- product identity does not match the evidence scope;
- evidence references are absent, invalid, expired, or outside scope for a material claim;
- engine response contains an unknown state or malformed field;
- engine response versions do not match the request;
- safety stop is paired with one or more options;
- engine failure is paired with candidate options;
- output contains an unauthorized execution instruction;
- output attempts to change client decisions or workflow state.

No guessed repair, silent coercion, or stale-output fallback is permitted. Preserve the last valid case record in the Case Store, but do not present it as the answer to the failed current run.

## 7. Versioning, decisions, and stop/restart behavior

- Case version and target version are assigned by Case Store/Orchestrator, never by the engine.
- A changed target creates a new target/case evaluation version.
- A changed datum invalidates only outputs that depend on that datum.
- Acceptance, execution consent, and specialist review do not automatically carry to a new version.
- Client question, rejection, acceptance, execution consent, and stop are separate explicit events.
- A rejected suggestion remains in the audit history but is not active.
- A client stop request is recorded by the workflow layer; only actually performed steps are recorded as performed.
- Automatic resume is prohibited. A later restart request triggers a fresh evaluation; it does not continue the stopped workflow.


### 7.1 Static audit — version ownership, suggestion validity, and stale-output suppression (2026-11-12)

This is a documentation-level consistency audit of Sections 4–7, the D-06/D-07 decision record, and fixtures S11–S15. It does not execute an Adapter, Orchestrator, Case Store, ledger, or product engine.

**Confirmed design invariants**

- Case Store/Orchestrator owns `case_version` and `target_version`; the engine cannot assign or advance either value.
- The engine response must identify the versions it evaluated. A response whose versions do not match its request is invalid.
- The Orchestrator must resolve an existing suggestion against the authoritative ledger before presenting it; the engine cannot mint, reactivate, or authoritatively set its status.
- A rejection remains auditable and excludes that exact suggestion/version from active options.
- D-06 requires publication-time suppression when the authoritative case or target version has changed, and prohibits publishing a previous successful response as the answer to a failed current run.
- Retry of the same logical request must preserve the same idempotency key and must not create a new case version or duplicate decision events.

**Gaps that remain open — do not infer**

1. **Idempotency key representation and scope:** Section 6 requires a stable key for a logical request, but Section 4 does not yet define a request field, key-generation owner beyond the Orchestrator boundary, uniqueness scope, retention window, or how a retry is distinguished from a new evaluation. No field name or policy is approved by this audit.
2. **Publication-time authority and race handling:** the Orchestrator is the publication authority in the call path, but the contract does not define the exact atomicity/compare-and-publish mechanism for checking the current `(case_version, target_version)` immediately before publication. The Adapter cannot independently establish currentness from an echoed response alone.
3. **Version-pair binding:** request examples include `case_version` and `target_version`; response examples use `evaluated_case_version` and `evaluated_target_version`. The contract does not yet specify a normative equality rule across request, response, authoritative current snapshot, and publication gate, including the handling of a target-only change.
4. **Suggestion identity and ledger binding:** S11's illustrative response includes `suggestion_ref`, `suggestion_version`, and ledger status, and its prose assigns their authority to the Orchestrator/ledger. The S12 fixture asserts rejection/deactivation but does not carry concrete suggestion and version identifiers. The exact reference shape, ledger lookup result, and binding to case/target versions remain unspecified.
5. **Stale-output scope in S15:** the fixture requires stale output suppression for the failed run, while D-06 prohibits a previous successful response from being reused as the answer to the failed current run. The exact correlation/run scope and retention of historical output for audit (as distinct from publication) are not defined here.
6. **Retry envelope details:** D-06 approves the invariant but leaves retryable failure classes and maximum attempts to versioned configuration. The failure example's `retryable` boolean is illustrative, not a complete retry protocol.

**Scenario traceability observations**

- **S11:** ledger validation before display is stated in prose; the fixture checks unchanged acceptance/consent and question-event recording, but does not assert that the referenced suggestion is still active and not rejected at publication time.
- **S12:** the fixture checks traceable rejection and absence from active options; it does not structurally identify the exact rejected suggestion/version or prove a ledger lookup.
- **S13:** the fixture checks new version creation, dependency re-evaluation, preservation of independent data, and no carry-forward of acceptance/consent. It does not specify the concrete version tuple or publication gate.
- **S14:** this is a Workflow Engine event, not an Adapter request. Its case version is shown, but target-version handling on a later fresh restart remains a workflow/orchestration detail.
- **S15:** the failure envelope correctly has `consultation_result: null` and no options. It does not define the atomic publication check or idempotency-key protocol.

**Conservative correction made during this audit:** one remaining illustrative datum in S01 used `source` instead of the D-07-approved `source_class`; it has been normalized to `source_class`. No fixture oracle, runner, schema, product behavior, or runtime interface was changed.

These are contract-definition gaps, not evidence that the approved invariants are wrong. Keep them open for a separately reviewed contract revision; do not fill them by implementation inference.


### 7.2 Static audit — suggestion identity, validity, and decision-ledger traceability (2026-11-12)

Scope: conceptual contract Sections 4–7 and 13, PO decisions D-01–D-08, the README scenario definitions, and machine-readable fixtures S11–S13. This is a static documentation audit only; no ledger, case store, adapter, or product behavior was executed.

**Confirmed design rules — internally consistent**

- Persistent suggestion identity and authoritative active/rejected status belong to the Orchestrator/Case Store and decision ledger; the engine may propose request-local candidates but cannot mint persistent references or assert authoritative status.
- Existing suggestions used in explanatory responses must be resolved from the authoritative ledger before display. The Orchestrator must reject forged, stale, mismatched, or rejected references.
- Rejection is a durable, auditable event for the exact suggestion/version. That exact rejected suggestion/version is excluded from active options; rejection does not force an engine or consultation response state.
- A replacement is not a continuation or reactivation of the rejected suggestion. It requires a fresh candidate evaluation and independent validation against current case/target data, constraints, and evidence.
- A question in S11 leaves acceptance and execution consent unchanged. A new target in S13 requires a new evaluation version; acceptance, execution consent, and specialist review do not automatically carry forward.

**Traceability gaps between human-readable scenarios and machine fixtures**

1. **S11 — existing suggestion reference:** the README scenario describes an existing V1 suggestion awaiting decision, and the illustrative response includes `suggestion_ref`, `suggestion_version`, and ledger-derived status. The machine fixture does not carry an explicit suggestion reference/version or an assertion that the referenced ledger entry is active and not rejected at publication. Its current assertions cover unchanged acceptance/consent and recording the question only.
2. **S12 — exact rejection target:** the README names a synthetic suggestion (`SUGGESTION-V1-A`) and requires rejection of that exact identifier/version. The machine fixture describes an active suggestion version V1 in `input_profile` and asserts traceability/deactivation, but contains no structured suggestion reference, suggestion version, rejection-event reference, or before/after ledger state. The exact target is therefore human-readable but not machine-bound in the current fixture.
3. **S13 — version transition:** the README describes `CASE-V1`/`CASE-V2`, a target change, and dependency-aware reevaluation. The machine fixture asserts that a new version is created and dependent outputs are rechecked, but does not provide an explicit prior/new case-version pair or target-version pair. It cannot, as currently shaped, establish exact version lineage.
4. **Ledger-to-case/target binding:** the contract requires current case/target versions and authoritative ledger resolution, but the design draft does not yet define the normative tuple or reference constraints that bind a suggestion record to its originating case version, target version, evaluation run, and decision events. Do not assume a field layout or retention rule.
5. **Validity/revalidation boundary:** the contract states that the Orchestrator re-resolves suggestion ledger, rejection state, case/target versions, workflow stop state, and evidence validity before publication. It does not yet define when a previously validated suggestion becomes invalid solely due to elapsed time, a changed datum, changed evidence status, or a changed workflow event beyond the existing dependency/version rules. Do not invent a time-to-live or automatic expiry policy.

**Audit conclusion**

The authority boundary and PO-approved rejection semantics are coherent. The remaining issue is not a conflicting PO decision; it is insufficient structured traceability in S11–S13 fixtures and unresolved ledger-reference/version-binding details. The README currently carries more scenario detail than the machine-readable fixture bundle. Preserve the current fixtures as synthetic contract descriptions, but do not describe them as proving ledger correctness or version-lineage behavior.

**No changes made to fixture JSON, JSON Schema, runner, tests, runtime interfaces, or product behavior.** The open items above require a separately reviewed contract/fixture proposal and, where they define new policy (for example expiry), explicit PO decision before implementation.

The general option invariant permits a separately evidenced alternative only in a different case where one actually passes all hard constraints; that possibility does not change S08's fixture oracle.

| Scenario | Expected behavior at contract boundary |
|---|---|
| S01 complete, supported case | Independent reasoned suggestion when all applicable data/evidence/safety gates pass; no mandatory human gate |
| S02 missing required history | `DATA_GAP`; request the specific missing datum; suppress dependent suggestion |
| S03 conflicting history | Preserve both sources and conflict; ask for resolution; do not choose one silently |
| S04 image-only case | Restrict visual claims; request required history/data; no inference of hidden chemical history or hair structure |
| S05 ambiguous product identity | Do not apply product-specific evidence until exact identity and scope match |
| S06 no applicable evidence | `KNOWLEDGE_GAP`; no invented rule or unsupported product recommendation |
| S07 safety alert | Safety-stop response; no options |
| S08 goal conflicts with constraint | State infeasibility or provide only a separately validated alternative; no invented replacement |
| S09 multiple valid options | Return only hard-constraint-valid options; deterministic ranking independent of input order; maximum three |
| S10 one valid option | Return exactly one valid option; do not fabricate alternatives |
| S11 question before decision | Answer the question; acceptance and execution consent remain unchanged |
| S12 explicit rejection | Record rejection in trusted case history; rejected suggestion is not active or reintroduced |
| S13 goal change | New version and fresh evaluation; invalidate dependent outputs; do not carry acceptance/consent |
| S14 client stop | Record stop; no automatic continuation; record only performed steps |
| S15 engine/retrieval failure | `ENGINE_FAIL`; suppress current run output and stale candidate output |

### Existing boundary subtests (not new scenario IDs)

- S09-R1: reverse option input order; ranking remains criteria-based.
- S13-R1: change an independent datum; unrelated outputs remain valid.
- S14-R1: restart requested after stop; require a fresh evaluation, never automatic resume.
- S15-R1: retrieval failure and rule-engine failure tested separately; both map to `ENGINE_FAIL`.
- S02/S03/S05/S06 control pairs: remove the specific defect while keeping other inputs constant; confirm the system can move to the appropriate next state when all remaining gates pass.

## 8.1 PO decisions — S06, S08, and S12 (approved 2026-11-12)

The Product Owner explicitly approved the following presentation and ledger rules. These decisions resolve the previously deferred items for these three fixtures; they do not approve the remaining wire enums or authorize implementation.

- **S06 — knowledge gap:** State plainly that no reliable applicable evidence is available. Withhold the suggestion or claim that depends on the missing knowledge. Do not guess, fabricate a rule, or relabel the case as `OUT_OF_V1_SCOPE` unless the requested claim/action is independently and formally outside V1. Refer for specialist review only where that is a justified next step; referral must not be used to disguise the evidence gap.
- **S08 — no valid alternative:** State that no valid option is available under the current documented constraints and explain the supported reason. Do not invent or display a substitute. A separately evidenced alternative may be considered only in a distinct fresh candidate evaluation if it independently passes all hard constraints; this does not alter S08's no-valid-alternative fixture oracle.
- **S12 — rejected suggestion:** Keep the exact rejected suggestion/version in the authoritative audit ledger and permanently exclude it from active options for that suggestion/version. Rejection does not force an engine state or consultation response state. If a genuinely independent alternative is possible, evaluate it in a fresh candidate run; otherwise explain that no valid alternative is available. Never reactivate or re-present the rejected suggestion as active.

### 9.12 Static audit — event ordering, concurrency, and stale publication races (2026-11-12)

Scope: contract Sections 2–7 and 9.10–9.11, D-06/D-07, the PO decision register Sections 6.1–6.7, and the current S11–S15 synthetic fixture descriptions. Static design audit only; no event store, evidence registry, ledger, workflow engine, publication gate, or product runtime was executed.

**Authority boundaries already established**

- Case Store/Orchestrator owns the authoritative case and target versions.
- The authoritative evidence source owns evidence identity, scope, and reviewed status; the engine cannot make an evidence reference current by echoing it.
- The authoritative decision ledger owns acceptance, rejection, and execution-consent history.
- Workflow Engine owns stop/restart workflow events and performed-step history.
- Orchestrator is responsible for deciding whether an engine result may be presented. The Adapter's validation of an echoed response is not, by itself, proof that all authoritative records remain current at publication time.

**Race-condition review and safe conclusions**

1. **Evidence revision after evaluation, before publication:** a result evaluated against an older or no-longer-applicable material evidence reference must not be published as a currently supported suggestion. The affected output requires fresh evaluation against current evidence. The contract does not define an evidence-revision token, dependency snapshot, or atomic check that binds the evidence state used by evaluation to the publication decision.
2. **Acceptance or execution consent concurrent with evidence revision:** acceptance and consent remain separate historical client events; neither can make invalid, conflicting, unverified, not-applicable, or outdated evidence authoritative. Preserve the historical events, but do not use them as a substitute for current evidence validation. The contract does not decide whether a prior decision is suspended, superseded, or requires reconfirmation.
3. **Client stop concurrent with evaluation/publication:** a stop is a distinct workflow event and automatic continuation is prohibited. If the authoritative workflow state indicates that the path has been stopped when a pending action is considered, the old run must not be used to continue that path. The precise race boundary—whether a simultaneous stop or publication is considered first—is not specified.
4. **Restart concurrent with a delayed old response:** restart requires a fresh evaluation. A delayed response from the stopped path must not be treated as the result of the fresh run or used to resume the old path. Existing case/target version checks help, but do not fully identify the workflow generation or evaluation run that a publication belongs to.
5. **Duplicate delivery, retry, or reordered events:** D-06 preserves the approved invariant that retrying the same logical request uses the same idempotency key and does not create duplicate decision events or a new case version. The exact event identity, ordering, deduplication scope, retention, and handling of out-of-order delivery remain unspecified.

**Minimum conservative publication principle**

A candidate must not be published as current if any authoritative input on which it depends is known to be stale, invalid, or superseded: case/target snapshot, material evidence applicability, suggestion/decision-ledger status, or relevant workflow stop state. A previous successful result is not a fallback answer for a failed or superseded current run. This restates existing fail-closed and ownership boundaries; it does not define an implementation-ready transaction protocol.

**Unresolved concurrency protocol — do not infer**

1. The exact linearization point for publication and the authoritative ordering of concurrent evidence, client-decision, workflow, and publication events.
2. Whether one atomic compare-and-publish operation must cover case/target versions, evidence revisions/dependencies, suggestion-ledger state, and workflow stop state; the current contract does not specify this.
3. The authoritative event sequence/version mechanism, clock semantics, or conflict resolution for simultaneous or out-of-order events.
4. The exact run/correlation identity needed to prevent a delayed response from an earlier evaluation or stopped workflow from being published after restart.
5. Idempotency-key field, generation/ownership details, uniqueness scope, retention, and the distinction between retrying one logical request and starting a new evaluation.
6. Treatment of a result already displayed, accepted, consented, or partly acted upon when a later authoritative revision arrives. Historical events must remain auditable; notification, reconfirmation, revocation, rollback, and remediation policies remain undecided.

**Conclusion:** the current design identifies the authoritative owners and several fail-closed outcomes, but it does not define a safe event-ordering or atomic publication protocol for concurrent changes. Do not select a timestamp-wins rule, lock strategy, transaction boundary, new version field, automatic revocation, notification, retry policy, or workflow state by implementation inference. These require a separately reviewed design proposal and PO decision where policy changes.

### 9.13 Design proposal — publication gate and concurrency control (2026-11-12)

**Status: proposed design for review; not approved, not an implementation contract.** This proposal translates the race findings in Section 9.12 into reviewable requirements while deliberately leaving the concrete transaction mechanism and policy decisions open.

**A. Separate two decisions**

1. **Advice publication:** whether a current, evidence-supported system response may be shown to the client.
2. **Service authorization:** whether a specific service step may proceed, based on the separately recorded client acceptance, explicit execution consent, current workflow state, and any other required authorization.

Advice publication must never be interpreted as acceptance, execution consent, or proof of performance. A service-authorization check must not be collapsed into the advice-publication check.

**B. Proposed logical publication preconditions**

At the moment the Orchestrator decides to publish a result, it should establish that all applicable authoritative inputs still match the evaluation context:

- the case and target context is still current;
- every material evidence dependency remains applicable to the exact claim/product/market/version scope used by the evaluation;
- the referenced suggestion remains the same suggestion/version and is not rejected or otherwise ineligible in the authoritative ledger;
- the relevant workflow path has not been stopped or superseded;
- the result belongs to the current evaluation/run, not a delayed response from an earlier run or pre-restart path;
- the current run has not failed and no previous response is being substituted as its answer.

If any required check fails, is unavailable, or cannot be reconciled, withhold the affected output and return a controlled non-publication/failure outcome; do not fall back to an older successful response. This is a proposed logical acceptance criterion derived from existing fail-closed boundaries, not a new wire state or field definition.

**C. Proposed concurrency requirement**

The checks above must be treated as one logical publication decision with a clearly defined linearization point: either the result is published against a coherent current snapshot, or it is not published. A sequence of independent reads followed by an unprotected publish is insufficient, because an authoritative record could change between the last read and publication.

This proposal does **not** choose the implementation mechanism. Options for engineering review:

| Option | Concept | Main advantage | Main limitation / review need |
|---|---|---|---|
| A. Serialized Orchestrator authority | Route relevant state-changing events and publication decisions through one authoritative coordinator/ordered command boundary | Clear ordering and one logical decision point | Requires confirmation that all relevant authorities can participate; potential throughput and availability trade-offs |
| B. Conditional commit across authoritative stores | Read authoritative revisions and publish only if all required revisions still match at commit | Can preserve separate ownership boundaries | Cross-store atomicity may not be available; requires a concrete consistency/compensation design |
| C. Snapshot validation followed by ordinary publish | Read current values, then publish without a conditional commit | Simple to implement | **Not sufficient as the safety mechanism**; leaves a time-of-check/time-of-use race |

**Working recommendation for architecture review:** adopt the *logical requirement* of one linearizable compare-and-publish decision, then evaluate Option A against the actual ownership/deployment topology. Do not treat Option A as approved or assume that a distributed transaction, lock, timestamp ordering, lease, or specific data field is already selected. Option B may be viable only if it can demonstrate equivalent atomicity. Option C alone should be rejected for safety-critical publication.

**D. Event and retry handling requirements to resolve**

- Define how a newly authoritative evidence revision invalidates only dependent outputs, including when case/target versions do not change.
- Define how stop and restart establish a new run boundary so delayed responses from the previous path cannot publish.
- Define event identity, idempotency scope, and deduplication for retries and duplicate delivery, while preserving D-06's same-logical-request retry invariant.
- Define the audit record for a rejected publication attempt and the reason it was withheld.
- Define what happens when an authoritative source is unavailable or returns conflicting revisions: fail closed for affected output; do not invent precedence.

No new field names, event IDs, revision counters, timestamps, TTLs, retry limits, lock types, transaction APIs, or workflow states are proposed here.

**E. Explicitly separate policy questions for PO**

The technical publication gate cannot decide whether an already accepted or consented client decision requires notification, renewed confirmation, suspension, or another client-facing action after material evidence changes. Nor can it decide remediation for work already partly performed. These remain separate PO policy decisions; historical events must remain auditable.

**F. Review acceptance criteria before any implementation proposal**

A future design should demonstrate, using synthetic sequences, at minimum:

1. evidence revision between evaluation and publication suppresses the dependent result;
2. acceptance/consent concurrent with evidence revision cannot make unsupported evidence publishable;
3. stop concurrent with evaluation prevents continuation of the stopped path;
4. restart prevents a delayed pre-restart response from being published as the new result;
5. duplicate retry does not create duplicate decision events or a new case version;
6. unrelated outputs remain eligible when only a separate dependency changes;
7. inability to establish a coherent current snapshot fails closed;
8. advice publication remains distinct from service authorization.

These are proposed test objectives only. They are not added to the current fixture bundle and are not claims of runtime behavior.

**Decision boundary:** this proposal is ready for architecture/PO review only. No PO decision was added, no schema or fixture was changed, and no implementation, pilot, release, or merge was authorized.

### 13.1 Mandatory provenance rule

A datum or evidence reference is not decision-grade merely because a model supplies a confidence value. Free-form model confidence is not a source, measurement, validation status, or substitute for provenance. A confidence field may be used only when its measurement method, calibration, scope, and owner are explicitly defined. Otherwise omit it.

For product-specific claims, the evidence registry must resolve the exact brand, line/series, product/shade, market, document revision, and applicable passage. A brand or shade code alone is not an identity match.

### 13.2 Publication-time ownership check

Before any candidate is shown, the Orchestrator must re-resolve the authoritative case/target versions, suggestion ledger, rejection state, workflow stop state, and evidence validity. If any relevant authority changed since evaluation, suppress the candidate and require a fresh evaluation or controlled revalidation. The engine response itself is never the source of truth for these records.

### 9.15 Proposed S11–S13 traceability model — review only (2026-11-12)

**Status: proposed documentation model; not an approved wire contract or implementation specification.** This section makes the missing relationships explicit without introducing JSON properties, enums, ledger events, expiry rules, or runtime behavior. The terms below describe the minimum conceptual references that a future machine-readable contract would need to bind. Their final representation, requiredness, and validation protocol remain subject to separate design review and PO approval where policy is affected.

#### A. Shared suggestion-to-case relationship

A persistent suggestion must be traceable, as one coherent relationship, to:

1. the authoritative case identity;
2. the case version and target version evaluated;
3. the persistent suggestion identity and its own version;
4. the evaluation-run identity that produced the candidate;
5. the authoritative decision-ledger history relevant to that exact suggestion/version (including acceptance or rejection, where present); and
6. the material evidence/dependency context used to assess that candidate, where applicable.

This is a conceptual reference tuple, not a proposed literal field list. The Case Store/Orchestrator remains authoritative for case and target versions; the authoritative ledger remains authoritative for persistent suggestion identity and decision status; the evaluation system owns only its run-local output; and the evidence authority owns evidence records and status. No component may substitute its own echo for another authority's record.

#### B. S11 — question about an existing suggestion

Before answering a question about an existing suggestion, the Orchestrator must resolve the suggestion relationship against the authoritative ledger and current case/target context. The suggestion may be referenced as current only if its identity/version belongs to the relevant case/target version and the ledger confirms it is eligible for display (not rejected or otherwise superseded under an already approved rule). The question and answer are separate interaction history; neither changes acceptance, rejection, or execution consent. If the authoritative relationship or status cannot be resolved, do not present the suggestion as currently active; explain the limitation or request the necessary review. The exact wire representation and any additional eligibility statuses remain unresolved.

#### C. S12 — rejection of an exact suggestion version

The rejection record must unambiguously identify the exact persistent suggestion and suggestion version, with enough authoritative case/target context to prevent a rejection from being applied to a different version or case. The ledger must preserve the rejection as historical decision evidence and exclude that exact suggestion/version from active options. A fresh alternative, if any, is a new candidate evaluation; it must not reuse the rejected suggestion as though it were active. The before/after ledger lookup and the precise event/reference representation are design requirements for future fixtures, not fields approved here. This section does not prescribe a new event name, ledger schema, or automatic transition.

#### D. S13 — target change and version pair

A target change must be traceable from the authoritative prior case/target version to the new case/target version created for the changed goal. The relationship must make it possible to distinguish: (a) the prior evaluated version; (b) the new target and its corresponding version; (c) dependent outputs requiring fresh evaluation; and (d) independent data/outputs that remain valid under existing dependency rules. Acceptance, execution consent, specialist review, and suggestions from the prior version do not automatically transfer to the new version. The exact version-generation mechanism and the required representation of the prior/new pair remain unresolved; no new version field or numbering algorithm is approved here.

#### E. Required future fixture coverage — not added in this revision

- **S11:** a synthetic existing suggestion is linked to a specific case/target version and evaluation run; ledger eligibility is checked immediately before display; a question/answer event leaves acceptance and execution consent unchanged.
- **S12:** a synthetic suggestion identity/version is resolved before rejection; the exact same identity/version is rejected; a subsequent active-options lookup excludes it while the historical rejection remains traceable.
- **S13:** synthetic prior and new case/target versions are explicit; the goal change creates a fresh evaluation boundary; dependent outputs are re-evaluated, independent data remains unchanged, and prior acceptance/consent/review are not carried forward.
- **Cross-scenario:** references that disagree on case, target, suggestion, or evaluation version are treated as unresolved/stale and cannot be repaired by inference.

#### F. Explicit unresolved decisions and exclusions

The following remain open: literal field names and nullability; ledger reference/event structure; evaluation-run identity and correlation scope; dependency-link representation; exact status/eligibility vocabulary; how version equality is checked at publication; time-based expiry and revalidation; and the atomicity/linearization mechanism across authorities. No TTL, expiry date, automatic revalidation, notification, reconfirmation, revocation, retry policy, or new workflow/response/engine state is introduced. Fixture JSON, JSON Schema, runner, tests, runtime, product behavior, and PO decisions are unchanged. This proposal does not authorize adapter implementation, engine integration, pilot, release, or merge.

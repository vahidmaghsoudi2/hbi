# HBI Consultation Engine Adapter Contract — Draft 0.2

- Status: design draft; not approved for implementation
- Scope: conceptual request/response boundary between the HBI Consultation Orchestrator and a consultation engine
- Repository branch: `docs/hair-color-independent-consultation-20261112`
- Related PR: #535 (must remain Draft and unmerged)
- Catalogue: the 88-color catalogue is out of scope and must not be modified
- Data policy: synthetic fixtures only in GitHub/CI; real customer data remains in the PO's offline local environment

## 1. Purpose and non-goals

The Adapter is a stateless contract boundary. It validates a request assembled by trusted HBI services, invokes the selected engine, validates the engine response, and returns a normalized result or a fail-closed error.

The Adapter is not the owner of:
- case records, case versions, or target versions;
- client questions, rejection, acceptance, or stop events;
- execution consent or authorization to perform a service;
- workflow transitions or recording performed steps;
- scientific evidence approval or product identity authority.

The Adapter does not execute chemical services, create formulas, infer product chemistry from similar shade numbers, or turn evidence availability into permission to issue chemical instructions.

This document defines no runtime API, database, JSON Schema, engine stub, production behavior, pilot, or release. Those require separate explicit approval.

## 2. System boundary and trust model

Expected call path:

1. Client/operator interaction is interpreted by the Consultation Orchestrator.
2. The Orchestrator obtains the authoritative case snapshot, case version, target version, prior suggestion ledger, customer decision events, and workflow state from trusted stores.
3. The Orchestrator resolves applicable policy and evidence references.
4. The Adapter validates the request envelope and passes a bounded context to the engine.
5. The engine returns a candidate consultation result.
6. The Adapter validates structure, references, version alignment, state compatibility, and safety invariants.
7. The Orchestrator applies case-history rules and decides what may be shown to the client.
8. Only the Workflow Engine may mutate workflow state. Case Store/Audit Log remain authoritative for case and event history.

The engine must not be trusted to authoritatively assert case history, customer decisions, workflow state, or execution consent. Such information is read-only context from trusted stores. A model-generated field cannot override the authoritative record.

## 3. Independent state layers

These layers must never be collapsed into one `primary_status`.

### 3.1 Engine/motor state — four conceptual states

The following identifiers are proposed for discussion; the four meanings are the previously agreed model:

| Proposed identifier | Meaning |
|---|---|
| `SUGGESTION_REVIEWABLE` | A reasoned candidate suggestion is available for review |
| `CONDITIONAL_SUGGESTION` | A suggestion is valid only if explicitly stated conditions are met |
| `NEEDS_MORE_INFORMATION` | Required information or test is missing |
| `STOP_OR_REFER_WITH_REASON` | The current run must stop or refer, with a reason |

A conditional suggestion is an engine state, not a sixth consultation response state.

### 3.2 Consultation response state — five approved meanings

The response state is one of the following five meanings, matching the README:

| Proposed identifier | Meaning |
|---|---|
| `SYSTEM_REASONED_SUGGESTION` | System can provide a reasoned, traceable suggestion |
| `NEEDS_INFORMATION_OR_TEST` | Missing information or test prevents a defensible suggestion |
| `NEEDS_IN_PERSON_OR_SPECIALIST_REVIEW` | Remote assessment is insufficient |
| `SAFETY_STOP_NO_EXECUTION_SUGGESTION` | Safety concern blocks an execution suggestion |
| `OUT_OF_V1_SCOPE` | Request is outside the approved first-version scope |

These identifiers are proposed wire values, not yet PO-approved enums. “Approved for execution” is a workflow decision, not a consultation response state.

### 3.3 Workflow state — ten states, owned elsewhere

The workflow remains the ten-state model already recorded in the project. The Adapter may return information useful to the Workflow Engine, but it must not mutate or claim ownership of any workflow state.

## 4. Request contract (conceptual)

A request contains:

- `contract_version`: contract version requested;
- `request_id`: unique request identifier generated by the Orchestrator;
- `operation`: one of `EVALUATE_CASE`, `ANSWER_QUESTION`, or `REEVALUATE`;
- `case_ref`, `case_version`, `target_version`: authoritative identifiers from Case Store;
- `case_context`: the minimum relevant, provenance-bearing case snapshot;
- `question`: present for a client question; not itself a decision event;
- `evidence_context`: references to evidence records, not model-invented evidence;
- `policy_context`: applicable versioned policy constraints.

`RESUME_CHECK` is not an operation. A client request to restart after stopping must be represented as a new evaluation request built from a fresh case snapshot, current goal, current safety information, current rules, and current evidence. It must never resume the old path automatically.

### 4.1 Data knowledge state and provenance

For every safety-relevant or decision-relevant datum, preserve the distinction between:
- `KNOWN`: a value is explicitly recorded;
- `UNKNOWN`: the real-world value is unknown;
- `NOT_ASKED`: the question has not been asked;
- `MISSING`: a required field was not supplied in this request/snapshot;
- `CONFLICT`: authoritative records disagree;
- `NOT_APPLICABLE`: the field does not apply.

These states are not interchangeable. In particular, `false` must not stand in for unknown or not asked.

Each datum should carry its source class, record reference, and recorded time where available. Source classes may include `CLIENT_REPORTED`, `OPERATOR_RECORDED`, `SPECIALIST_OBSERVED`, `PRODUCT_DOCUMENT`, `INSTRUMENT_MEASURED`, and `SYSTEM_DERIVED`. A derived value must never be represented as a direct client report or physical observation.

### 4.2 Exact product identity

Where product-specific evidence is required, its identity must resolve to the exact brand, line/series, product/shade, market, and document/version scope. Similar brand names, shade numbers, or codes do not establish chemical equivalence.

## 5. Response contract (conceptual)

A successful engine response contains:
- request and case identifiers;
- evaluated case and target versions;
- one engine state;
- one of the five consultation response states;
- reason codes, separate from state values;
- a client-readable summary;
- zero or more candidate options;
- conditions, missing information, evidence references, limitations, and next step.

The Adapter's transport/validation result is separate from the engine's consultation result. A malformed engine response is an Adapter/engine failure, not a consultation status.

### 5.1 Reason codes

At minimum, distinguish:
- `DATA_GAP`: relevant case data is insufficient;
- `KNOWLEDGE_GAP`: applicable, reliable knowledge/evidence is unavailable;
- `ENGINE_FAIL`: engine, retrieval, or processing failed;
- `CONFLICTING_DATA`: relevant recorded sources conflict;
- `SAFETY_CONCERN`: a safety constraint blocks an execution suggestion;
- `OUT_OF_SCOPE`: the request is outside the approved scope;
- `STALE_CASE_VERSION`: the evaluated snapshot is no longer current.

These are diagnostic/reason codes, not additional consultation states. `DATA_GAP`, `KNOWLEDGE_GAP`, and `ENGINE_FAIL` must remain distinguishable.

### 5.2 Option invariants

- A safety-stop response must contain an empty `options` array.
- An engine failure must not publish any candidate option from the failed run.
- A candidate without applicable, traceable evidence must not be returned as an executable suggestion.
- Only valid options that pass all hard constraints may be ranked.
- If three valid options exist, no more than three are returned; if only one is valid, return exactly one; never invent options to fill a quota.
- Ranking must not depend on input array order.
- Each candidate option is bound to the evaluated target/case version. The engine may return candidate content and a request-local candidate key, but it cannot mint or assert an authoritative suggestion_ref, suggestion history, or active/rejected status. The Orchestrator/Case Store assigns the persistent suggestion identifier and records the candidate only after validation. For an explanatory question such as S11, any referenced existing suggestion must be resolved from the authoritative ledger; the engine cannot create or reactivate it.
- Rejected suggestions are filtered using the authoritative suggestion ledger, not by trusting the engine to remember rejections.
- A question does not change acceptance or execution consent.
- Acceptance of a suggestion is not execution consent.
- The engine cannot create or modify acceptance, consent, stop events, performed steps, or workflow state.

### 5.3 Chemical instruction boundary

The field `chemical_instruction_allowed` is intentionally absent. The V1 contract does not grant the engine authority to emit formulas, oxidant percentages, processing times, or other chemical execution instructions. Evidence alone does not grant such authority. Any future change requires explicit PO approval and separate specialist/evidence validation.

## 6. Fail-closed validation rules

The Adapter/Orchestrator must reject or suppress the current run when:
- contract version is unsupported;
- request or case identifiers do not match;
- case or target version is stale;
- required data is missing or contradictory and materially affects the decision;
- product identity does not match the evidence scope;
- evidence references are absent, invalid, expired, or outside scope for a material claim;
- engine response contains an unknown state or malformed field;
- engine response versions do not match the request;
- safety stop is paired with one or more options;
- engine failure is paired with candidate options;
- output contains an unauthorized execution instruction;
- output attempts to change client decisions or workflow state.

No guessed repair, silent coercion, or stale-output fallback is permitted. Preserve the last valid case record in the Case Store, but do not present it as the answer to the failed current run.

## 7. Versioning, decisions, and stop/restart behavior

- Case version and target version are assigned by Case Store/Orchestrator, never by the engine.
- A changed target creates a new target/case evaluation version.
- A changed datum invalidates only outputs that depend on that datum.
- Acceptance, execution consent, and specialist review do not automatically carry to a new version.
- Client question, rejection, acceptance, execution consent, and stop are separate explicit events.
- A rejected suggestion remains in the audit history but is not active.
- A client stop request is recorded by the workflow layer; only actually performed steps are recorded as performed.
- Automatic resume is prohibited. A later restart request triggers a fresh evaluation; it does not continue the stopped workflow.

### Existing boundary subtests (not new scenario IDs)

- S09-R1: reverse option input order; ranking remains criteria-based.
- S13-R1: change an independent datum; unrelated outputs remain valid.
- S14-R1: restart requested after stop; require a fresh evaluation, never automatic resume.
- S15-R1: retrieval failure and rule-engine failure tested separately; both map to `ENGINE_FAIL`.
- S02/S03/S05/S06 control pairs: remove the specific defect while keeping other inputs constant; confirm the system can move to the appropriate next state when all remaining gates pass.

## 8.1 PO decisions — S06, S08, and S12 (approved 2026-11-12)

The Product Owner explicitly approved the following presentation and ledger rules. These decisions resolve the previously deferred items for these three fixtures; they do not approve the remaining wire enums or authorize implementation.

- **S06 — knowledge gap:** State plainly that no reliable applicable evidence is available. Withhold the suggestion or claim that depends on the missing knowledge. Do not guess, fabricate a rule, or relabel the case as `OUT_OF_V1_SCOPE` unless the requested claim/action is independently and formally outside V1. Refer for specialist review only where that is a justified next step; referral must not be used to disguise the evidence gap.
- **S08 — no valid alternative:** State that no valid option is available under the current documented constraints and explain the supported reason. Do not invent or display a substitute. A separately evidenced alternative may be considered only in a distinct fresh candidate evaluation if it independently passes all hard constraints; this does not alter S08's no-valid-alternative fixture oracle.
- **S12 — rejected suggestion:** Keep the exact rejected suggestion/version in the authoritative audit ledger and permanently exclude it from active options for that suggestion/version. Rejection does not force an engine state or consultation response state. If a genuinely independent alternative is possible, evaluate it in a fresh candidate run; otherwise explain that no valid alternative is available. Never reactivate or re-present the rejected suggestion as active.

## 13. Field ownership and traceability matrix (design control)

This matrix makes the trust boundary explicit. It is a documentation control only; it does not define a runtime schema or authorize implementation.

| Field / data group | Authoritative owner | Engine/Adapter permission | Validation and publication rule |
|---|---|---|---|
| `contract_version` | Adapter contract registry / Orchestrator configuration | Read only | Reject unsupported versions; never infer or silently upgrade |
| `request_id`, `operation` | Orchestrator | Read only | Validate format and allowed operation; retries retain the same idempotency identity |
| `case_ref`, `case_version`, `target_version` | Case Store | Read only | Must match the authoritative snapshot at request and publication time |
| `case_context` and datum values | Case Store / originating record owner | Read only, minimum necessary subset | Preserve each datum's knowledge state, source, record reference, and timestamp; no model-generated overwrite |

| Prior suggestions, rejection, acceptance, execution consent | Case Store / Audit Log | Read-only context; no creation or mutation | Resolve active/rejected status from ledger; reject forged, stale, or mismatched references |
| Workflow state, stop events, performed steps | Workflow Engine / Audit Log | Read-only context; no transition or event authoring | Only Workflow Engine records stop/transition/performed-step events; restart requires fresh evaluation |

| `summary`, limitations, explanation | Engine drafts; Orchestrator owns publication | Draft text only | Validate against evidence, scope, safety, and prohibited-instruction rules before display |
| Candidate option content and rationale | Engine proposes; Orchestrator validates | Candidate only | Every material claim needs applicable evidence; hard constraints precede ranking; no unsupported substitute |
| Persistent `suggestion_ref`, version, active/rejected status | Orchestrator / Case Store | Engine cannot mint or assert | Assign and record only after validation; existing references must resolve through the authoritative ledger |

| Adapter failure code, stage, retryability, correlation reference | Adapter / Orchestrator | Engine error may be diagnostic input | Adapter constructs the failure envelope; retryability follows versioned policy, never model discretion |
| Output suppression / stale-output decision | Orchestrator, using Case Store version | No engine authority | Recheck current version immediately before publication; suppress stale or failed-run output |

### 13.1 Mandatory provenance rule

A datum or evidence reference is not decision-grade merely because a model supplies a confidence value. Free-form model confidence is not a source, measurement, validation status, or substitute for provenance. A confidence field may be used only when its measurement method, calibration, scope, and owner are explicitly defined. Otherwise omit it.

For product-specific claims, the evidence registry must resolve the exact brand, line/series, product/shade, market, document revision, and applicable passage. A brand or shade code alone is not an identity match.

### 13.2 Publication-time ownership check

Before any candidate is shown, the Orchestrator must re-resolve the authoritative case/target versions, suggestion ledger, rejection state, workflow stop state, and evidence validity. If any relevant authority changed since evaluation, suppress the candidate and require a fresh evaluation or controlled revalidation. The engine response itself is never the source of truth for these records.

### 13.3 Mapping caveat — fixture oracle is not a wire-state decision

# HBI Customer Reality Gate Audit V0.1

## Scope

Bounded repository-level verification of whether the current HBI master contains **verified Customer-Originated Language Evidence** suitable for Phase 2.1 Customer Language Discovery.

This audit does not create a corpus, extract expressions, modify implementation, or open Gate 2.

- Phase 2.1: BLOCKED BY EVIDENCE GAP

## Verification standard

A repository source is eligible only when all are evidenced:

1. persisted source material exists;
2. customer origin is established;
3. provenance is traceable;
4. the material is permitted/appropriate for Phase 2 use.

Capability, schema, API, UI, documentation, synthetic fixtures, and test data do not satisfy this standard by themselves.

## Repository findings

### 1. Persisted customer/consultation/feedback corpus

The repository tree at the baseline was inspected for persisted data artifacts and customer/consultation/feedback paths.

No committed database, SQLite database, CSV/NDJSON customer corpus, or equivalent persisted Customer/Consultation/Feedback dataset was found in the baseline tree.

The repository contains application models and services for these concepts, but those are implementation capability, not Customer Reality Evidence.

### 2. Customer model

`app/models/customer.py` defines a Customer model with fields including `concerns`, `observations`, `answers`, `case_history`, and `operator_notes`.

Finding:

`MODEL/CAPABILITY ONLY`

No committed real Customer records were found that establish customer origin and provenance.

### 3. Feedback model and customer-response capability

`app/models/feedback.py` defines Feedback with `source`, `outcome`, `rating`, and `comment`.

The consultation/customer-response tests demonstrate that a CUSTOMER feedback path can be exercised.

Finding:

`CAPABILITY + SYNTHETIC TEST EVIDENCE`

The tests create their own records and comments. For example, `tests/test_consultation_response_vertical_slice_001.py` creates named test customers and a test feedback comment. This is test data, not verified customer reality.

### 4. Consultation vertical-slice tests

`tests/test_consultation_vertical_slice_001.py` creates test Customer and Case records and exercises intake/consultation behavior.

Finding:

`SYNTHETIC TEST DATA`

These records are generated by the test and do not establish real customer-originated source material.

### 5. Seed data

`scripts/seed_test_db.py` creates explicitly test products and labels them as fixtures.

`scripts/seed_products_from_records.py` seeds product/evidence data only. No customer-language corpus is supplied by this seed path.

Finding:

`NOT CUSTOMER LANGUAGE SOURCE`

### 6. Test fixtures containing customer-like language

The baseline contains tests with strings such as customer names and consultation concerns, including Persian concern examples.

Finding:

`SYNTHETIC / TEST`

They are authored as test inputs. No provenance establishes that these strings were imported from real customers.

### 7. Discovery documentation

The discovery artifacts establish the framework, criteria, source registry, and acquisition decision.

Finding:

`DOCUMENTARY / METHODOLOGICAL SOURCE`

They do not constitute Customer Reality Evidence.

## Required evidence to change the decision

A future source may reopen verification only when actual source material is supplied with:

- exact source location/identifier;
- customer-origin status;
- direct vs reported status;
- provenance method;
- applicable privacy/confidentiality boundary;
- permission/authorization for Phase 2 use.

Until then, absence of a committed corpus remains an **Evidence Gap**, not permission to synthesize one.

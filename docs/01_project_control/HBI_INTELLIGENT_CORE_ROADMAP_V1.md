## اصل مرکزی

HBI یک **سیستم تصمیم‌یار** برای درک و تشخیص مسئله، ارزیابی گزینه‌ها و پیشنهاد محصول است؛ **نه صرفاً** یک سیستم پیشنهاد محصول.

### زنجیره اصلی

```
مراجعه‌کننده
↓
پرونده مشتری
↓
مسئله / مشکل
↓
تشخیص و ارزیابی
↓
عوامل مؤثر
↓
شواهد
↓
اطلاعات ناقص / متعارض
↓
سؤال یا مشاهده تکمیلی
↓
تشخیص به‌روز
↓
نیاز
↓
الزامات محصول
↓
محصولات موجود
↓
حذف گزینه‌های نامناسب
↓
رتبه‌بندی
↓
پیشنهاد
↓
دلیل پیشنهاد + میزان اطمینان
↓
تصمیم متخصص
↓
نتیجه واقعی
```

## ۰. اصل ارتباط‌پذیری و ردیابی اطلاعات (V1.1)

هر اطلاعاتی که وارد هسته HBI می‌شود باید **جایگاه، زمینه، منشأ، رابطه و کاربرد تصمیمی** قابل ردیابی داشته باشد.

این اصل **به این معنا نیست** که هر داده الزاماً باید مستقیماً به یک Problem متصل باشد.

### تفکیک موجودیت‌ها / لایه‌های اطلاعات

| لایه | نقش |
|------|------|
| اطلاعات مشتری | Customer Profile |
| اطلاعات مراجعه فعلی | Current Case |
| شکایت / مسئله | Problem |
| مشاهده یا ارزیابی | Assessment |
| عامل مؤثر | Factor |
| شواهد | Evidence |
| دانش عمومی | Knowledge / Rule |
| نیاز پرونده | Need |
| الزام محصول | Product Requirement |
| محصول | Product Master |
| پیشنهاد | Recommendation |
| تصمیم انسانی | Human Decision |
| نتیجه واقعی | Outcome |

برای اطلاعات عمومی مانند Rule یا Knowledge نیز باید **دامنه کاربرد، شرایط کاربرد، و رابطه با تصمیم** قابل ردیابی باشد.

**اصل معماری:**  
داده بدون رابطه، لزوماً دانش نیست؛ دانش بدون زمینه، لزوماً قابل استفاده برای تصمیم نیست.

---

## ۱. تشخیص، رکن اصلی HBI است

HBI ابتدا باید تلاش کند مسئله مراجعه‌کننده را بفهمد و در حد اطلاعات و شواهد موجود تشخیص دهد.

تشخیص نباید صرفاً یک برچسب باشد. باید قابل ردیابی باشد:

```
تشخیص
├── عوامل مؤثر
├── شواهد
├── مشاهدات
├── اطلاعات گفته‌شده توسط مراجعه‌کننده
├── اطلاعات سابقه
├── اطلاعات نامعلوم
├── تعارض‌ها
├── فرضیه‌ها
└── میزان اطمینان
```

**سه اصل الزامی طراحی:**

1. **عامل، علت قطعی نیست.**  
2. **عامل با سؤال یکی نیست.**  
3. **نامعلوم به معنی ردشده نیست.**

---

## ۲. سؤال باید تابع تشخیص باشد، نه برعکس

سیستم نباید یک پرسشنامه ثابت اجرا کند.

```
وضعیت فعلی پرونده
↓
شکاف اطلاعاتی
↓
عوامل مؤثر بر تصمیم
↓
انتخاب سؤال یا مشاهده مناسب
↓
پاسخ / مشاهده
↓
شاهد جدید
↓
به‌روزرسانی تشخیص
```

HBI باید در هر لحظه بتواند بگوید:  
**برای بهتر شدن تصمیم فعلی، چه اطلاعاتی هنوز لازم است؟**

---

## ۳. از داشته‌های فعلی پروژه استفاده می‌کنیم

دارایی‌های فعلی دور ریخته نمی‌شوند و **بازطراحی غیرضروری ممنوع** است.

از جمله (بدون ادعای کامل‌بودن پیاده‌سازی هر مورد — وضعیت دقیق فقط پس از F0 Reality Audit):

- پروفایل مشتری  
- محصول و اطلاعات هویتی  
- ورود و پذیرش محصول  
- شواهد  
- دانش محصول  
- ثبت و بررسی شواهد  
- خدمات / APIهای موجود محصول  
- کنترل وضعیت محصول  
- کنترل دسترسی  
- ثبت تغییرات  
- آزمون‌های موجود  
- سازوکارهای حاکمیتی  
- منطق فعلی ارزیابی و پیشنهاد  

کار اصلی اکنون **اتصال، تکمیل و اعتبارسنجی** این اجزا در یک مسیر واقعی است.

---

## ۴. نخست یک مسیر واقعی را کامل می‌کنیم

برای سرعت، همه مسائل و همه محصولات را همزمان نمی‌سازیم.

یک حوزه واقعی و پرتکرار انتخاب می‌شود و این مسیر برای آن کامل می‌شود:

```
مشتری → پرونده → مسئله → تشخیص → شواهد → تکمیل اطلاعات
→ نیاز → محصولات واجد شرایط → ارزیابی → پیشنهاد → توضیح → نتیجه
```

این یک **برش عمودی واقعی** است، نه یک نمونه نمایشی.

---

## ۵. دو مرحله برای انتخاب محصول

**ابتدا — صلاحیت / حذف:** محصولات فاقد شرط لازم حذف می‌شوند.  
**سپس — رتبه‌بندی:** فقط میان واجدین شرایط.

این دو **نباید مخلوط شوند.**

---

## ۶. وزن‌دهی فعلاً دست‌کاری نمی‌شود

منطق و وزن‌های موجود تا تصمیم رسمی جدید، مبنا می‌مانند. هدف فعلی اثبات زنجیره است، نه فرمول جدید.

---

## ۷. پیشنهاد باید قابل توضیح باشد

خروجی نباید فقط امتیاز باشد؛ باید مسئله، تشخیص، شواهد استفاده‌شده، UNKNOWN، حذف‌ها، ترجیح، و اطمینان را توضیح دهد. دلیل بخشی از خود تصمیم است.

---

## ۸. انسان در تصمیم نهایی باقی می‌ماند

```
HBI → تشخیص + استدلال + پیشنهاد → متخصص گالری → تأیید/اصلاح/رد → مراجعه‌کننده
```

---

## ۹. نتیجه واقعی از همان ابتدا ثبت می‌شود

نتیجه یک مشتری **خودکار حقیقت عمومی نمی‌شود.** تجربه مشتری، شاهد محصول، و دانش معتبر جدا می‌مانند.

## ۱۰. F0 — Reality Audit و Capability Map (V1.1)

اولین فاز عملیاتی پس از قفل این نقشه راه:

**F0 — HBI CORE BASELINE & REALITY AUDIT**

Reality Audit فقط «وجود/عدم وجود» نیست. برای هر قابلیت یا اطلاعات مهم:

| پرسش | محتوا |
|------|--------|
| کجا وجود دارد؟ | مسیر / ماژول / جدول / سند |
| مالک چیست؟ | Owner مفهومی |
| به چه موجودیت/مرحله‌ای مربوط است؟ | Case / Problem / Factor / … |
| رابطه با زنجیره تصمیم چیست؟ | Relation |
| چه تصمیمی را پشتیبانی می‌کند؟ | Decision Use |
| آیا واقعاً در مسیر تصمیم استفاده می‌شود؟ | Wired / Not wired |
| منشأ و ردیابی؟ | Provenance |
| وضعیت | Existing / Partial / Missing / Unknown / Conflict |

### قالب پیشنهادی Capability Map

```
Capability / Data | Status | Owner | Relation | Decision Use | Evidence
```

**Evidence** یعنی ارجاع Repository واقعی (مسیر فایل، تست، commit) — نه ادعا.

خروجی F0: Capability Map + Gap List + Execution Package اولیه.  
**هیچ Implementation صرفاً به‌خاطر وجود Roadmap مجاز نیست.**

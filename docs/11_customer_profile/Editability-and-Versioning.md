# قابلیت ویرایش و نسخه‌بندی واحد پروفایل مشتری

## اصل
واحد باید **قابل ویرایش در نسخه‌های بعدی** باشد بدون شکستن Pilot و بدون از دست رفتن تاریخچه.

## قواعد
1. قراردادها با شماره نسخه (`v1`, `v2`) نام‌گذاری می‌شوند.
2. Schema additive اولویت دارد؛ حذف/تغییر معنای فیلد نیاز به Migration + Audit دارد.
3. Factهای CONFIRMED با ویرایش مشتری/فروشنده → نسخه جدید + SUPERSEDED روی قبلی.
4. Consent قابل revoke است؛ revoke تاریخچه را پاک نمی‌کند، دسترسی آینده را محدود می‌کند.
5. Timeline رویدادها append-only هستند؛ اصلاح با رویداد تصحیحی.
6. هر تغییر سیاست Promotion / Freshness در Decision Log ثبت می‌شود.

## مسیر انتشار نسخه بعدی
```
پیشنهاد تغییر → بررسی PO/Qwen1 → به‌روزرسانی Contract+Dictionary
→ Migration Plan → تست پذیرش → اجرا روی branch → Merge با مجوز
```
